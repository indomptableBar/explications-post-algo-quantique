1. Introduction

Les algorithmes post-quantiques (PQC) sont des algorithmes cryptographiques conçus pour résister aux attaques menées par des ordinateurs quantiques. Avec l'avancement de l'informatique quantique, les algorithmes classiques comme RSA et ECC deviennent vulnérables. Ce guide vous explique comment migrer vers des algorithmes post-quantiques pour protéger vos certificats numériques sous Linux.

💡 Pourquoi agir maintenant ?
La stratégie "Harvest Now, Decrypt Later" signifie que les données chiffrées aujourd'hui avec RSA/ECC pourraient être déchiffrées demain par un ordinateur quantique. Il est crucial de migrer vers des algorithmes PQC dès maintenant.

Prérequis

  • Système Linux (Ubuntu 24.04+, Debian 12+, Fedora 40+, ou distributions récentes)
  • Accès root ou sudo
  • Connexion Internet pour l'installation des paquets
  • Connaissances de base en cryptographie et gestion de certificats

2. Comprendre la menace quantique

🧠 Algorithmes classiques

RSA repose sur la factorisation de grands nombres. ECC repose sur le problème du logarithme discret elliptique. Un ordinateur quantique suffisamment puissant pourrait résoudre ces problèmes avec l'algorithme de Shor.

⚡ Impact de Shor

L'algorithme de Shor peut factoriser un nombre à 2048 bits en quelques heures sur un ordinateur quantique. Cela briserait RSA-2048, ECDSA, et ECDH utilisés dans la majorité des certificats TLS actuels.

🛡 Grover aussi menace AES

L'algorithme de Grover divise par 2 la sécurité des fonctions de hachage et du chiffrement symétrique. AES-128 devient aussi sûr qu'AES-64 classique. Solution : passer à AES-256.

⚠ Timeline estimée : Les experts estiment qu'un ordinateur quantique capable de casser RSA-2048 pourrait apparaître entre 2030 et 2040. Les données sensibles avec une durée de vie supérieure doivent être protégées dès maintenant.

3. Principaux algorithmes post-quantiques

Voici les principales familles d'algorithmes post-quantiques :

🔗 Cristal-Kyber Standard NIST

Type : Encapsulation de clé (KEM)
Famille : Réseaux euclidiens
Usage : Échange de clés, chiffrement de certificats
Tailles : Kyber-512 (NIST Level 1), Kyber-768 (NIST Level 3), Kyber-1024 (NIST Level 5)

🔑 Crystal-Dilithium Standard NIST

Type : Signature numérique
Famille : Réseaux euclidiens
Usage : Signatures de certificats, code signing
Tailles : Dilithium2, Dilithium3, Dilithium5

✍ Falcon Standard NIST

Type : Signature numérique
Famille : NTRU / Réseaux euclidiens
Avantage : Signatures plus compactes que Dilithium
Inconvénient : Implémentation plus complexe

🔓 SPHINCS+ Standard NIST

Type : Signature numérique (basée sur le hachage)
Famille : Hash-based signatures
Avantage : Hypothèses de sécurité minimales
Inconvénient : Signatures et clés plus volumineuses

💰 ML-KEM FIPS 203

Type : Module-Lattice KEM
Note : Standardisation officielle de Kyber par le NIST
Implémentations : OpenSSL 4.0+, BoringSSL, liboqs

🔑 ML-DSA FIPS 204

Type : Module-Lattice Signature
Note : Standardisation officielle de Dilithium par le NIST
Implémentations : OpenSSL 4.0+, BoringSSL, liboqs

4. Standards NIST (FIPS)

Le NIST a finalisé en 2024 les premiers standards post-quantiques :

Standard Algorithme Usage Date
FIPS 203 ML-KEM (Module-Lattice KEM) Échange de clés Août 2024
FIPS 204 ML-DSA (Module-Lattice Sig) Signature numérique Août 2024
FIPS 205 SLH-DSA (SPHINCS+) Signature basée sur hachage Août 2024

5. Installation sous Linux

5.1 OpenSSL 4.0+ avec support PQC

OpenSSL 3.5 (et suivants) intègre le support natif des algorithmes post-quantiques ML-KEM et ML-DSA.

1

Installer OpenSSL 4.0+ depuis les dépôts

# Ubuntu / Debian
sudo apt update
sudo apt install -y openssl libssl-dev

# Vérifier la version
openssl version
# Devrait afficher: OpenSSL 3.x.x ou supérieur
2

Compiler OpenSSL depuis les sources (si nécessaire)

# Installer les dépendances de compilation
sudo apt install -y build-essential perl zlib1g-dev

# Télécharger et compiler OpenSSL 3.5
wget https://github.com/openssl/openssl/releases/download/openssl-3.5.0/openssl-3.5.0.tar.gz
tar -xzf openssl-3.5.0.tar.gz
cd openssl-3.5.0
./Configure --prefix=/usr/local/openssl enable-ktls enable-ec_nistp_64_gcc_128
make -j$(nproc)
sudo make install

# Mettre à jour le PATH
echo 'export PATH=/usr/local/openssl/bin:$PATH' | sudo tee /etc/profile.d/openssl.sh
source /etc/profile.d/openssl.sh
3

Vérifier le support PQC dans OpenSSL

# Lister les algorithmes KEM disponibles
openssl list -kem-algorithms 2>/dev/null | grep -i kem

# Lister les algorithmes de signature
openssl list -signature-algorithms 2>/dev/null | grep -iE "ml-dilithium|falcon|sphincs|mldsa"

# Vérifier les algorithmes supportés
openssl list -public-key-algorithms | grep -i "kem\|mldsa\|falcon"

5.2 Liboqs (Open Quantum Safe)

La bibliothèque liboqs fournit une collection d'implémentations d'algorithmes PQC pour des tests et évaluations.

# Installer les dépendances
sudo apt install -y cmake gcc g++ git libssl-dev

# Cloner et compiler liboqs
git clone https://github.com/open-quantum-safe/liboqs.git
cd liboqs
mkdir build && cd build
cmake -DCMAKE_INSTALL_PREFIX=/usr/local -DBUILD_SHARED_LIBS=ON ..
make -j$(nproc)
sudo make install

# Mettre à jour le cache des bibliothèques
sudo ldconfig

5.3 OQS-OpenSSL (fork PQC)

# Cloner le fork OpenSSL avec support PQC complet
git clone https://github.com/open-quantum-safe/openssl.git oqs-openssl
cd oqs-openssl
./Configure --prefix=/usr/local/oqs-openssl enable-oqs
make -j$(nproc)
sudo make install

6. Générer des certificats avec algorithmes PQC

6.1 Générer une clé et un certificat auto-signé avec ML-DSA

ML-DSA (FIPS 204) est la standardisation de Dilithium pour les signatures numériques.

# Générer une clé privée ML-DSA (Dilithium)
openssl genpkey -algorithm mldsa44 -out server_mldsa44.key
# mldsa44 = Dilithium2 (NIST Level 1)
# mldsa65 = Dilithium3 (NIST Level 3)
# mldsa87 = Dilithium5 (NIST Level 5)

# Générer le CSR (Certificate Signing Request)
openssl req -new -key server_mldsa44.key -out server_mldsa44.csr \
    -subj "/C=FR/ST=Ile-de-France/L=Paris/O=MonOrganisme/CN=example.com"

# Auto-signer le certificat
openssl x509 -req -in server_mldsa44.csr \
    -signkey server_mldsa44.key \
    -out server_mldsa44.crt \
    -days 365

# Vérifier le certificat
openssl x509 -in server_mldsa44.crt -text -noout | head -20

6.2 Générer un certificat avec Falcon

# Clé Falcon-512
openssl genpkey -algorithm falcon512 -out server_falcon512.key

# Clé Falcon-1024
openssl genpkey -algorithm falcon1024 -out server_falcon1024.key

# CSR et auto-signature
openssl req -new -key server_falcon512.key -out server_falcon512.csr \
    -subj "/CN=example.com"
openssl x509 -req -in server_falcon512.csr \
    -signkey server_falcon512.key \
    -out server_falcon512.crt -days 365

6.3 Générer un certificat avec SPHINCS+

# Clé SPHINCS+ (basée sur le hachage, plus lente mais très sécurisée)
openssl genpkey -algorithm sphincssha2128fsimple -out server_sphincs.key

# CSR et auto-signature
openssl req -new -key server_sphincs.key -out server_sphincs.csr \
    -subj "/CN=example.com"
openssl x509 -req -in server_sphincs.csr \
    -signkey server_sphincs.key \
    -out server_sphincs.crt -days 365

6.4 Comparaison des tailles

Algorithme Taille clé privée Taille clé publique Taille signature
RSA-2048 (classique) ~1.2 Ko ~256 octets ~256 octets
ECDSA P-256 (classique) ~32 octets ~65 octets ~72 octets
ML-DSA-44 (mldsa44) ~2.5 Ko ~1.3 Ko ~2.4 Ko
ML-DSA-65 (mldsa65) ~4 Ko ~1.9 Ko ~3.3 Ko
Falcon-512 ~1.3 Ko ~896 octets ~666 octets
Falcon-1024 ~2.3 Ko ~1.8 Ko ~1.3 Ko
SPHINCS+-128f ~64 octets (seed) ~32 octets ~17 Ko

7. Chiffrement de certificats avec ML-KEM (Kyber)

ML-KEM (FIPS 203) est l'algorithme standardisé d'encapsulation de clé pour l'échange de clés. Il peut chiffrer des données comme des certificats.

7.1 Chiffrer un certificat avec ML-KEM

1

Générer une paire de clés ML-KEM

# Générer une clé ML-KEM-768 (recommandé)
openssl genpkey -algorithm ML-KEM-768 -out kem_priv.pem
# Niveaux disponibles :
# ML-KEM-512  = NIST Level 1
# ML-KEM-768  = NIST Level 3 (recommandé)
# ML-KEM-1024 = NIST Level 5

# Extraire la clé publique
openssl pkey -in kem_priv.pem -pubout -out kem_pub.pem
2

Chiffrer un fichier certificat

# Créer un certificat de test
openssl req -x509 -newkey rsa:2048 -keyout /dev/null \
    -out mon_certificat.pem -days 365 -nodes \
    -subj "/CN=test.example.com"

# Chiffrer le certificat avec ML-KEM
openssl pkeyutl -encap -inkey kem_pub.pem \
    -out cert_chiffre.bin \
    -secret secret.bin

# Utiliser le secret partagé pour chiffrer AES-256-GCM
openssl enc -aes-256-gcm -salt -pbkdf2 \
    -in mon_certificat.pem \
    -out mon_certificat_chiffre.enc \
    -pass file:secret.bin
3

Déchiffrer le certificat

# Déchiffrer avec la clé privée ML-KEM
openssl pkeyutl -decap -inkey kem_priv.pem \
    -encaps cert_chiffre.bin \
    -secret secret_dechiffre.bin

# Déchiffrer le certificat
openssl enc -d -aes-256-gcm -pbkdf2 \
    -in mon_certificat_chiffre.enc \
    -out mon_certificat_dechiffre.pem \
    -pass file:secret_dechiffre.bin

# Vérifier
openssl x509 -in mon_certificat_dechiffre.pem -text -noout
⚠ Note : ML-KEM est un algorithme d'encapsulation de clé, pas de chiffrement direct. Le flux typique est : ML-KEM encapsule une clé secrète, puis cette clé est utilisée pour chiffrer les données avec AES-256-GCM (chiffrement symétrique).

8. SSH avec clés post-quantiques

OpenSSH 9.x supporte les clés post-quantiques pour les échanges de clés.

1

Installer OpenSSH avec support PQC

# Vérifier la version d'OpenSSH
ssh -V
# Nécessite OpenSSH 9.0+ pour le support natif des clés PQC

# Sur Ubuntu 24.04+
sudo apt install -y openssh-server

# Sur les systèmes plus anciens, compiler depuis les sources
git clone https://github.com/openssh/openssh-portable.git
cd openssh-portable
autoreconf -i
./configure --with-ssh1
make
sudo make install
2

Générer une clé SSH post-quantique

# Générer une clé SSH avec ML-KEM pour l'échange de clés
# OpenSSH utilise hybride PQC + classique par défaut
ssh-keygen -t ssh-ed25519 -O "kex_algorithms=curve25519-sha256,ssh-userauth-pq@openquantumsafe.org:kem-ml-kem-768-sha256@openquantumsafe.org"

# Ou utiliser le format natif pour le quantum-safe
ssh-keygen -t ssh-mlkem768 -f ~/.ssh/id_ml-kem

# Alternative : clé hybride
ssh-keygen -t ed25519 -O "kex-algorithms=curve25519-sha256,ml-kem-768-sha256"
3

Configurer le serveur SSH pour le PQC

# Éditer /etc/ssh/sshd_config
sudo nano /etc/ssh/sshd_config

# Ajouter / modifier ces lignes :
KexAlgorithms curve25519-sha256,ml-kem-768-sha256,diffie-hellman-group16-sha512
HostKeyAlgorithms ssh-ed25519,ssh-mlkem768,rsa-sha2-512
PubkeyAcceptedAlgorithms ssh-ed25519,ssh-mlkem768,rsa-sha2-512

# Redémarrer le service
sudo systemctl restart sshd

# Tester la connexion
ssh -vv -o "KexAlgorithms=ml-kem-768-sha256" user@server
✔ Hybride recommandé : En production, utilisez des clés hybrides (classique + PQC). Si l'algorithme PQC est compromis, la sécurité classique reste intacte.

9. TLS 1.3 avec échange de clés PQC

TLS 1.3 peut utiliser ML-KEM pour l'échange de clés durante la poignée de main.

9.1 Configurer Nginx avec PQC

# /etc/nginx/nginx.conf ou site-specific config
server {
    listen       443 ssl;
    server_name  example.com;

    # Certificat signé avec ML-DSA
    ssl_certificate     /etc/ssl/certs/server_mldsa65.crt;
    ssl_certificate_key /etc/ssl/private/server_mldsa65.key;

    # Support des groupes de clés PQC pour l'échange
    ssl_ecdh_curve X25519MLKEM768:X25519Kyber768Draft00;

    # Cipher suites compatibles TLS 1.3 avec PQC
    ssl_conf_command Ciphersuites TLS_AES_256_GCM_SHA384:TLS_CHACHA20_POLY1305_SHA256;

    # Support des groupes de clés hybrides
    ssl_groups X25519MLKEM768:P-256:P-384;

    location / {
        proxy_pass http://localhost:8080;
    }
}

9.2 Tester la connexion TLS PQC

# Tester avec openssl s_client
openssl s_client -connect example.com:443 \
    -groups X25519MLKEM768 \
    -ciphersuites TLS_AES_256_GCM_SHA384

# Vérifier les paramètres de la poignée de main
openssl s_client -connect example.com:443 -groups X25519MLKEM768 2>&1 | grep "Server Temp Key"
# Sortie attendue : Server Temp Key: X25519MLKEM768, ECDH, ...

# Tester avec curl
curl --ciphers TLS_AES_256_GCM_SHA384 \
     --tls13-ciphers TLS_AES_256_GCM_SHA384 \
     -v https://example.com

10. OpenSSL 4.0+ : Support natif PQC

OpenSSL 3.5 intègre le support natif des standards NIST ML-KEM (FIPS 203) et ML-DSA (FIPS 204).

10.1 Commandes de chiffrement ML-KEM

# Générer une clé ML-KEM-768
openssl genpkey -algorithm ML-KEM-768 -out kem_key.pem

# Extraire la clé publique
openssl pkey -in kem_key.pem -pubout -out kem_pub.pem

# Encapsuler une clé secrète (chiffrement côté client)
openssl pkeyutl -encap -inkey kem_pub.pem \
    -out ciphertext.bin \
    -secret shared_secret.bin

# Décapsuler la clé secrète (déchiffrement côté serveur)
openssl pkeyutl -decap -inkey kem_key.pem \
    -encaps ciphertext.bin \
    -secret shared_secret.bin

# Vérifier que les secrets sont identiques
diff secret.bin shared_secret.bin && echo "OK : Clé dérivée correctement"

10.2 Signatures ML-DSA

# Générer une clé ML-DSA-65
openssl genpkey -algorithm ML-DSA-65 -out dsa_key.pem

# Signer un fichier
openssl pkeyutl -sign -inkey dsa_key.pem \
    -in document.txt -out document.sig

# Vérifier la signature
openssl pkeyutl -verify -inkey dsa_key.pem \
    -in document.txt -sigfile document.sig

10.3 Créer une autorité de certification PQC

# 1. Générer la clé CA (Autorité de Certification)
openssl genpkey -algorithm ML-DSA-87 -out ca_mldsa.key

# 2. Créer le certificat auto-signé de la CA
openssl req -new -x509 -key ca_mldsa.key \
    -out ca_mldsa.crt -days 3650 \
    -subj "/C=FR/O=MonOrganisme-CA/CN=Ma CA PQC"

# 3. Générer la clé du serveur
openssl genpkey -algorithm ML-DSA-65 -out serveur.key

# 4. Créer le CSR du serveur
openssl req -new -key serveur.key -out serveur.csr \
    -subj "/CN=www.example.com"

# 5. Signer le certificat du serveur avec la CA
openssl x509 -req -in serveur.csr \
    -CA ca_mldsa.crt -CAkey ca_mldsa.key \
    -CAcreateserial -out serveur.crt -days 365

# 6. Vérifier la chaîne
openssl verify -CAfile ca_mldsa.crt serveur.crt

11. Récapitulatif des commandes

Génération de clés

# ML-KEM (Kyber)
openssl genpkey -algorithm ML-KEM-512 -out key.pem
openssl genpkey -algorithm ML-KEM-768 -out key.pem
openssl genpkey -algorithm ML-KEM-1024 -out key.pem

# ML-DSA (Dilithium)
openssl genpkey -algorithm ML-DSA-44 -out key.pem
openssl genpkey -algorithm ML-DSA-65 -out key.pem
openssl genpkey -algorithm ML-DSA-87 -out key.pem

# Falcon
openssl genpkey -algorithm falcon512 -out key.pem
openssl genpkey -algorithm falcon1024 -out key.pem

Encapsulation / Décapsulation

# Encapsuler (client)
openssl pkeyutl -encap \
  -inkey pub.pem \
  -out cipher.bin \
  -secret secret.bin

# Décapsuler (serveur)
openssl pkeyutl -decap \
  -inkey priv.pem \
  -encaps cipher.bin \
  -secret secret.bin

Signature / Vérification

# Signer
openssl pkeyutl -sign \
  -inkey mldsa_key.pem \
  -in file.txt \
  -out file.sig

# Vérifier
openssl pkeyutl -verify \
  -inkey mldsa_key.pem \
  -in file.txt \
  -sigfile file.sig

Vérification de certificats

# Info certificat
openssl x509 -in cert.pem -text -noout

# Vérifier signature
openssl verify -CAfile ca.pem cert.pem

# Voir l'algorithme utilisé
openssl x509 -in cert.pem \
  -text -noout | grep -A2 "Public Key Algorithm"

12. Bonnes pratiques

✔ Migration hybride

Utilisez des clés hybrides (classique + PQC) pendant la transition. Cela protège contre les compromissions futures de l'un ou l'autre algorithme.

🛡 Niveaux de sécurité

Pour la sécurité maximale, utilisez ML-KEM-1024 ou ML-DSA-87. Pour un bon compromis performance/sécurité, ML-KEM-768 / ML-DSA-65 est recommandé.

💾 Stockage des clés

Protégez les clés privées avec des modules HSM ou des fichiers chiffrés. Les clés post-quantiques sont plus volumineuses, adaptez votre infrastructure.

🔍 Audit et logging

Tenez un inventaire de tous les certificats PQC. Surveillez les algorithmes utilisés dans vos infrastructures avec des outils de monitoring.

⚡ Performance

Les algorithmes PQC sont plus coûteux en CPU et en bande passante. Testez les performances avant de déployer en production. Les signatures SPHINCS+ sont particulièrement lentes.
